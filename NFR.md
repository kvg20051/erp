# Нефункциональные требования к ERP-системе

**Домен портала:** [wax.su](https://wax.su)

**WAX — Workflows. Automation. eXecution.**

*Процессы. Автоматизация. Исполнение.*

**Версия:** 0.1  
**Дата:** 14 ноября 2026 года  
**Статус:** проект для согласования

## 1. Назначение и область применения

Документ определяет нефункциональные требования (NFR) к ERP-системе: веб-приложению, API, мобильному клиенту, базе данных и интеграциям.

Требования распространяются на ядро, справочники, финансы, закупки, продажи, склад и дополнительные модули по мере их реализации. Размещение — на собственных виртуальных машинах или выделенных серверах.

Все численные значения ниже — **предлагаемые целевые показатели первой промышленной версии**, а не результаты измерений и не уже согласованные обязательства. Их необходимо подтвердить с учётом бюджета, состава модулей и нагрузочного тестирования.

## 2. Базовые допущения

| Параметр | Предлагаемое значение |
|---|---|
| Зарегистрированные пользователи | 100 |
| Одновременно активные пользователи | 30 |
| Объём деловых документов для испытаний | 100 000 документов, суммарно 1 000 000 строк |
| Объём вложений | 50 ГБ |
| Постоянная нагрузка | 10 запросов в секунду |
| Кратковременный пик | 30 запросов в секунду в течение 5 минут |
| Сетевая задержка при испытаниях | RTT не более 100 мс |
| Среды | Разработка, тестирование / staging, production |
| Организационная структура | Несколько юридических лиц с разграничением доступа |

Профиль нагрузочных испытаний должен отражать реальные операции: просмотр списков, поиск, открытие, сохранение и проведение документов, формирование отчётов. Соотношение операций и состав тестовых данных фиксируются перед испытаниями.

## 3. Производительность и масштабирование

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-P01 | Чтение карточек, списков и поиск должны выполняться не более чем за 2 секунды для 95% запросов при базовой нагрузке. | Нагрузочный тест на согласованном наборе данных; p95 ≤ 2 с. |
| NFR-P02 | Сохранение и проведение документов объёмом до 100 строк должно выполняться не более чем за 3 секунды для 95% запросов. | Нагрузочный тест соответствующих операций; p95 ≤ 3 с. |
| NFR-P03 | Доля технически неуспешных запросов при согласованной нагрузке должна быть менее 0,5%. | Отчёт испытаний. Ожидаемые отказы в доступе и ошибки пользовательского ввода учитываются отдельно. |
| NFR-P04 | Длительные отчёты, массовые импорты и другие продолжительные операции должны выполняться в фоне с отображением состояния и результата. | Запуск операции не блокирует интерфейс; пользователь видит статус и может получить результат либо описание ошибки. |
| NFR-P05 | Большие списки должны использовать серверную пагинацию и ограничение размера выдачи. | Проверка API и интерфейса на больших наборах данных; отсутствие загрузки всего списка в клиент. |
| NFR-P06 | Веб-приложение и API должны поддерживать горизонтальное масштабирование. | Работа двух экземпляров приложения за балансировщиком без потери пользовательской сессии и нарушения целостности операций. |

Время ответа API измеряется от отправки запроса до получения ответа. Отдельно проверяется время отображения результата в интерфейсе. Выбор фонового режима не отменяет необходимости согласовать сроки выполнения конкретных массовых операций.

## 4. Доступность и восстановление

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-A01 | Доступность production должна составлять не менее 99,5% за календарный месяц, включая плановые работы. | Внешний мониторинг основных пользовательских сценариев; доля времени успешной работы за месяц. |
| NFR-A02 | Допустимая потеря данных при аварии — не более 15 минут (RPO). Восстановление базы и вложений должно обеспечивать согласованное состояние. | Контрольное восстановление с проверкой времени последней доступной операции и целостности ссылок на вложения. |
| NFR-A03 | Восстановление сервиса после аварии должно занимать не более 4 часов (RTO) на подготовленной чистой VM. | Учебное восстановление по инструкции с фиксацией начала и окончания. |
| NFR-A04 | Резервные копии должны шифроваться и храниться вне основного сервера с отдельными правами доступа. | Проверка настроек хранения, шифрования и доступа. |
| NFR-A05 | Успешность резервного копирования проверяется ежедневно; контрольное восстановление проводится не реже одного раза в квартал. | Журналы проверок и протоколы восстановления. |
| NFR-A06 | Недоступность внешней системы не должна приводить к бесконечному ожиданию или потере принятых операций. Интеграции должны иметь тайм-ауты и безопасные повторные попытки. | Испытания при отключённой внешней системе, восстановлении соединения и повторной доставке. |

RPO для вложений требует отдельного механизма резервирования, если они хранятся вне базы данных. Наличие копий базы само по себе не подтверждает выполнение NFR-A02.

## 5. Целостность и корректность данных

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-D01 | Проведение документа должно быть атомарным: все связанные изменения фиксируются вместе либо полностью отменяются. | Искусственный сбой в ходе проведения не оставляет частично записанных движений. |
| NFR-D02 | Повторный запрос на создание или проведение с тем же идентификатором операции не должен создавать дубликаты. | Повтор запроса после тайм-аута и при повторной доставке возвращает прежний результат либо однозначный статус операции. |
| NFR-D03 | Одновременное редактирование должно выявлять конфликт версий и исключать незаметную перезапись чужих изменений. | Два пользователя изменяют один объект; второй получает уведомление о конфликте. |
| NFR-D04 | Денежные значения должны храниться и рассчитываться с фиксированной десятичной точностью. Правила округления должны быть едиными и документированными. | Проверка типов данных и тестов граничных значений, округления, сумм строк и итогов. |
| NFR-D05 | Исправление проведённых документов должно сохранять историю и связь с исходной операцией. | Можно установить, кто, когда и каким документом изменил учётный результат. |
| NFR-D06 | Ограничения закрытых периодов, прав доступа и правил учёта запасов должны проверяться сервером, включая обращения через API. | Попытки обхода ограничений прямыми API-запросами отклоняются. Правила отрицательных остатков определяются отдельно. |
| NFR-D07 | Интеграционные события, связанные с зафиксированными бизнес-операциями, не должны теряться при сбое процесса. | Сбой между записью документа и отправкой события не приводит к потере события; повтор не создаёт дубликат результата. |
| NFR-D08 | Технические временные метки и учётные даты должны различаться. Правила часовых поясов должны быть едиными. | Проверки операций на границе суток и периода, отображения в разных часовых поясах. |

## 6. Безопасность и аудит

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-S01 | Доступ должен разграничиваться по ролям, юридическим лицам и области доступных данных. | Матрица ролей и отрицательные тесты доступа к данным другой организации. |
| NFR-S02 | Проверка прав должна применяться ко всем каналам: интерфейсу, API, вложениям, отчётам и экспорту. | Прямые обращения по идентификатору или URL не дают обходить ограничения. |
| NFR-S03 | Для административных учётных записей обязательна многофакторная аутентификация. | Административный вход без второго фактора невозможен; проверен регламент восстановления доступа. |
| NFR-S04 | Вход должен быть защищён от перебора паролей ограничением частоты попыток и журналированием неудачных входов. | Серия неудачных попыток вызывает ограничение; события фиксируются без записи пароля. |
| NFR-S05 | Передача данных между клиентами и сервером должна выполняться по HTTPS. | Проверка TLS и отсутствия передачи учётных данных по незашифрованному соединению. |
| NFR-S06 | Пароли, ключи и другие секреты не должны храниться в репозитории, образах или открытых логах. Секреты разделяются по средам. | Проверка репозитория, сборки, журналов и настроек окружений. |
| NFR-S07 | Значимые действия должны иметь аудит: инициатор, время, действие, объект, результат и идентификатор запроса. | По журналу можно восстановить последовательность создания, изменения, проведения и отмены документа, а также изменения прав. |
| NFR-S08 | Обычный бизнес-пользователь не должен иметь возможности изменять или удалять аудит. Предлагаемый срок хранения — не менее 12 месяцев. | Проверка прав и политики хранения. Окончательный срок согласуется отдельно. |
| NFR-S09 | Блокировка пользователя и отзыв сессии или токена должны прекращать соответствующий доступ не позднее чем через 5 минут. | Проверка ранее выданных сессий и токенов после отзыва. |

## 7. API, интеграции и мобильный клиент

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-I01 | Публичные API должны иметь версионируемый контракт OpenAPI, соответствующий реализации. | Контракт включён в репозиторий; автоматические проверки выявляют расхождения. |
| NFR-I02 | Несовместимые изменения API должны выпускаться в новой версии с описанием миграции. Предыдущая версия поддерживается не менее 90 дней после объявления замены. | Проверка политики версионирования и совместимости клиентских приложений. |
| NFR-I03 | API должен возвращать единый формат ошибок с машинным кодом, понятным сообщением и идентификатором запроса. | Контрактные тесты ошибок валидации, доступа, конфликтов и внутренних сбоев. |
| NFR-I04 | Импорт должен предоставлять отчёт о принятых и отклонённых строках и позволять безопасно повторять обработку. | Повторный импорт не создаёт дубликаты; причины отклонения доступны пользователю. |
| NFR-I05 | Мобильный клиент должен корректно обрабатывать потерю соединения и неопределённый результат отправки операции. | После восстановления связи пользователь получает достоверный статус; повторная отправка не дублирует операцию. |
| NFR-I06 | До выпуска мобильного приложения фиксируется матрица поддерживаемых ОС, версий приложения и API. | Испытания на согласованной матрице, включая предыдущие поддерживаемые версии клиента. |

Полноценная автономная работа мобильного клиента без сети не включена в базовые требования. При необходимости для неё отдельно определяются правила локального хранения, синхронизации и разрешения конфликтов.

## 8. Удобство использования

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-U01 | Интерфейс должен понятно показывать состояние документа, результат действия и возможный следующий шаг. | Проверка основных сценариев от создания до завершения или отмены документа. |
| NFR-U02 | Ошибки ввода должны указывать поле и способ исправления; введённые корректные данные не должны теряться. | Проверка валидации обязательных полей, форматов и бизнес-ограничений. |
| NFR-U03 | Основной язык интерфейса — русский. Веб-клиент должен работать в согласованных версиях Chrome, Edge и Firefox. | Проверка основных сценариев по утверждённой матрице браузеров. |

## 9. Наблюдаемость и эксплуатация

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-O01 | Запросы и фоновые операции должны иметь идентификаторы корреляции для поиска связанных событий. | По идентификатору можно связать обращение пользователя, обработку API и фоновые действия. |
| NFR-O02 | Должны контролироваться доступность, ошибки, задержки, очереди, свободное место и резервное копирование. Оповещение о критическом сбое — не позднее 5 минут после его обнаруживаемого возникновения. | Искусственный сбой вызывает уведомление ответственному; проверены пороги и канал доставки. |
| NFR-O03 | Логи не должны содержать пароли, токены и лишние персональные данные. | Проверка примеров журналов и автоматических правил маскирования. |
| NFR-O04 | Для развёртывания, диагностики, восстановления и отката должны быть актуальные инструкции. | Выполнение процедур по инструкции на тестовой среде без недокументированных действий. |

## 10. Сопровождение и выпуск изменений

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-M01 | Изменения должны иметь прослеживаемость: требование → спецификация → код → тест → выпуск. | Для выбранного изменения доступны связанные артефакты в системе управления разработкой и репозитории. |
| NFR-M02 | Критические сценарии должны иметь автоматические проверки: учётные операции, права, идемпотентность и конкурентное изменение данных. | Тесты выполняются в CI; нарушение проверяемого правила блокирует выпуск. |
| NFR-M03 | Выпуск должен проходить сборку, тестирование и проверку на staging с сохранением результатов. | Для версии доступны протокол CI, результаты тестов и решение о выпуске. |
| NFR-M04 | В production должен попадать тот же неизменяемый образ, который проверен на staging. | Совпадает digest образа; повторной сборки между средами нет. |
| NFR-M05 | Изменения базы должны оформляться версионируемыми миграциями с проверкой прерывания и повторного запуска. | Миграция проверена на тестовой копии данных; известны время выполнения и порядок восстановления после сбоя. |
| NFR-M06 | Для каждого выпуска должен быть определён способ возврата к работоспособной версии с учётом совместимости схемы базы данных. | На staging выполнен откат приложения либо согласованный сценарий восстановления; подтверждена сохранность данных. |

## 11. Приёмка

Перед первым промышленным выпуском необходимо выполнить:

1. Проверить права доступа, целостность учётных операций и ограничения закрытых периодов.
2. Провести нагрузочные испытания на согласованном объёме данных и профиле операций.
3. Проверить сбои интеграций, повторные запросы, конкурентное изменение и прерывание операций.
4. Восстановить систему на чистой VM из резервных копий и измерить фактические RPO и RTO.
5. Выполнить развёртывание через staging и проверить сценарий отката или восстановления.
6. Подготовить отчёт о выполнении требований: результат по каждому ID, доказательства проверки, отклонения и решение по ним.

Отклонения фиксируются явно: причина, риск, ответственное лицо, срок устранения и условия допуска к эксплуатации.

## 12. Вопросы для согласования

До утверждения документа необходимо определить:

- Отрасль и особенности учёта, включая правила проведения и исправления документов.
- Юрисдикцию, обязательные требования к персональным данным и сроки хранения.
- Состав модулей первой версии и критические сквозные процессы.
- Фактическое число пользователей, рост данных и профиль нагрузки.
- Допустимость простоев, целевые RPO/RTO и бюджет инфраструктуры.
- Необходимость автономной работы мобильного приложения.
- Поддерживаемые версии браузеров, мобильных ОС и клиентских приложений.
- Сроки выполнения фоновых отчётов, импортов и закрытия периода.
- Ответственных за эксплуатацию, реагирование на инциденты и приёмку.
