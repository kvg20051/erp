# wax — работающий прототип ERP

**Домен портала:** [wax.su](https://wax.su)

**WAX — Workflows. Automation. eXecution.**

*Процессы. Автоматизация. Исполнение.*

Версия 0.1 • 14.11.2026  
Основание: репозиторий kvg20051/erp, commit 6894da5a2772f94290d3c6e214d9810c72c8edc7; fr.md 0.3, STACK.md 0.4, NFR.md, INFRA.md.

Это запускаемый прототип первой фазы, а не завершённая ERP и не подтверждение выполнения всех NFR. Мобильный клиент и реальный обмен с 1С в первую фазу не входят. Все известные ограничения перечислены в [матрице требований](docs/REQUIREMENTS.md). До их устранения используйте синтетические данные.

## Что уже можно делать

- Войти, выбрать доступное юридическое лицо; назначить пользователю бизнес-роли и заблокировать доступ.
- Вести номенклатуру, контрагентов, склады, подразделения, должности, курсы и другие справочники.
- Создать заказ поставщику; отправить его на согласование; руководителю — согласовать; кладовщику — оформить поступление с серийными номерами.
- Создать заказ клиента, зарезервировать товар, выписать частичный счёт, зарегистрировать оплату и провести отгрузку.
- Получить остатки на дату и валовую прибыль по реализации; оформить возврат или перемещение; выдать оборудование сотруднику.
- Создать карточку сотрудника, оформить приём, согласовать отсутствие, сформировать и закрыть табель; скачать пакет-заглушку для 1С.
- Проверить оборудование перед увольнением; увольнение блокирует доступ сотрудника в ERP.
- Добавить комментарий и вложение к документу; скачать PDF; выгрузить сотрудников, остатки и прибыль в CSV/XLSX.
- Проверить аудит, запрет изменения проведённого документа, закрытие периода, конфликт версий и повтор запроса.

## Архитектура поставленного прототипа

~~~mermaid
flowchart LR
  Browser["React / Ant Design"] -->|HTTPS| Nginx
  Nginx -->|"/api/v1"| API["Java 25 / Spring Boot 4.1"]
  Nginx -->|"/auth"| KC["Keycloak · OIDC / MFA"]
  API --> PG[("PostgreSQL 18")]
  API --> Files[("Файлы · Docker volume")]
  KC --> KCDB[("Отдельная БД Keycloak")]
  PG --> Outbox["Таблица событий / пакет 1С"]
  Backup["Согласованный snapshot DB + files"] --> Restic["Опциональный off-host restic"]
~~~

Backend — один процесс с пакетами core, mdm, documents, hrm, api. Проведение документа, движение, аудит и запись события выполняются в одной транзакции. Для защиты от гонок записи сериализуются по юридическому лицу. Это простой механизм прототипа; его пропускная способность должна проверяться нагрузочным тестом.

**Отличия от целевого STACK.md:** используется Spring JDBC вместо JPA/jOOQ; границы пакетов пока не проверяются Spring Modulith. Нет JobRunr, отдельного worker, RLS, S3, Nexus, SOPS/age, полноценной observability и DB-реплики. Outbox сохраняется, но автоматической отправки и retry-worker нет. Ansible Vault применяется вместо SOPS. Это технический долг, а не незаметная смена согласованной архитектуры.

## Локальный запуск

Нужны Java 25, Maven 3.9, Node.js 24 и npm. Для PDF и тестов на Linux установите fonts-dejavu-core; на Windows используется Arial. Команды выполняются из корня проекта.

Терминал 1, Linux/macOS:

~~~bash
mvn -f backend/pom.xml verify
export DEMO_PASSWORD="$(openssl rand -hex 16)"
printf 'Пароль локальной демонстрации: %s\n' "$DEMO_PASSWORD"
cd backend
java -jar target/nixu-0.1.0.jar --spring.profiles.active=demo --server.address=127.0.0.1
~~~

В PowerShell:

~~~powershell
mvn -f backend/pom.xml verify
$env:DEMO_PASSWORD = Read-Host "Пароль локальной демонстрации, не менее 12 символов"
Set-Location backend
java -jar target/nixu-0.1.0.jar --spring.profiles.active=demo --server.address=127.0.0.1
~~~

Терминал 2, из корня проекта:

~~~bash
cd apps/web
npm ci
npm run dev
~~~

Откройте http://127.0.0.1:5173. Пользователи: admin, purchasing, manager, warehouse, sales, hr, employee. В локальной демонстрации у них один заданный вами пароль. Этот режим не публикуют в Интернет. Данные сохраняются в backend/data; H2 используется только для автономной демонстрации. На VPS используется PostgreSQL и Keycloak.

## Первый сквозной пример

1. Войти как purchasing. Документы → создать заказ поставщику: USD, склад wh-main, server, 5 шт., цена без НДС 1000. Сохранить → На согласование.
2. Выйти, войти как manager. Открыть заказ → Согласовать. Автор не может согласовать собственный документ.
3. purchasing проводит согласованный заказ.
4. warehouse открывает заказ → Цепочка документов → Создать поступление. Ввести пять разных серийных номеров, по одному в строке. Провести.
5. sales создаёт заказ клиента: три server по 1500 USD; проводит и резервирует.
6. Из заказа создать счёт на половину суммы: три позиции по 750 USD вместо 1500. Провести. На вкладке «Оплаты» записать сумму счёта.
7. warehouse создаёт реализацию из заказа: три server по 1500 USD, серийные номера из поступления. Провести.
8. Проверить склад: осталось две единицы. В отчёте прибыли выручка берётся без НДС в рублях, стоимость — по отгруженным единицам.

В тестовых справочниках задан учебный курс USD = 90 и учебная ставка НДС 20%. Это тестовые значения, не утверждение об актуальном курсе или применимой налоговой ставке. Для рабочего контура задайте собственные справочники и согласованные правила.

## Персонал

Карточку можно сохранить неполной. Перед приёмом требуются имя, фамилия, отчество или признак отсутствия, дата рождения, телефон, адрес, паспорт, подразделение, должность, руководитель. В демо ID подразделения — department, должности — position.

При создании пользователя на VPS:
1. Администратор создаёт его в Keycloak, задаёт временный пароль. Обязательное действие CONFIGURE_TOTP включено по умолчанию.
2. В wax → Администрирование указывает тот же логин, роли и юрлица.
3. В карточке сотрудника указывает этот логин. Автосоздание учётной записи из кадровой карточки пока не реализовано.
4. Увольнение запрещено, пока оборудование не возвращено. При увольнении business grant блокируется немедленно; сессия Keycloak отдельно не удаляется, но API ERP перестаёт её принимать.

Для табеля предварительно заполните производственный календарь. Без календаря прототип считает рабочими понедельник–пятницу: праздники РФ автоматически не загружаются. Кадровые события будущей датой пока запрещены.

## API

Контракт первой версии: [contracts/openapi.json](contracts/openapi.json). JWT должен иметь issuer вашего Keycloak и audience nixu-api. Провайдерские ключи WUXU здесь не используются.

POST документов требует Idempotency-Key. Повтор того же ключа с тем же содержимым возвращает тот же документ, с другим — HTTP 409. Редактирование и переходы требуют текущую version. Денежные расчёты выполняются на сервере с BigDecimal/NUMERIC.

## Важные границы учёта

- Документы на склад разрешены только не раньше последней даты движения по юрлицу. Пересчёт задним числом отсутствует.
- Несерийные запасы считают среднюю стоимость по складу, а ТЗ требует по юрлицу: до исправления не используйте их для реального учёта.
- Проведённый складской документ отменять напрямую нельзя; используйте предусмотренный возврат. Универсальная корректировка и сторно не реализованы.
- НДС берётся из текущей карточки номенклатуры и фиксируется в документе. Временная история ставок пока отсутствует.
- Порог согласования заказов задаётся в политике организации, по умолчанию 1000 USD. Скидка свыше 10% требует согласования; порог скидки пока фиксирован.
- Роли фиксированы; их произвольный конструктор, заместители и ограничение руководителя только своим подразделением ещё не реализованы.
- Список сотрудников ограничен 1000, справочники — 500, журнал аудита — последними 300 записями. Это не полная реализация NFR-P05 для всех списков.
- Уведомления представлены очередью событий. Email и персональный inbox не реализованы.
